Method · Epistemics

How a reader tells what a system knows from what it generated.

Five provenance classes, ordered, with the weakest propagating through anything derived from them. One class exists specifically for language-model output. The whole thing is enforced by a validator with no override flag, because a labelling discipline that depends on discipline does not survive a deadline.

This page is the specification, written to be lifted. Nothing below is specific to this site except the examples.

The problem

A system that mixes live data, computed output, human judgement and language-model text presents all four to the reader as text on a page. They look identical. A number fetched from NOAA this morning and a number a model invented render in the same font, and the reader has no way to tell them apart except to trust the author.

That failure is getting worse, not better, because language models produce fluent, confident, well-structured prose that reads exactly like a finding. The usual response is a disclaimer at the bottom of the page, which nobody reads and which applies uniformly to content that is not uniform.

The alternative is to make provenance a property of each value, carried with it, rendered differently, and checked by a machine.

The five classes

Each answers one question: who says so? The classes are rendered from a single definition in shared.js, so this page cannot drift from the pages that use them.

The order is a knob, not a discovery

weakest → strongest

That ordering encodes a policy: that human judgement outranks machine argument, and that derivability outranks assertion. It is this project's setting. It is not a fact about the world, and an adopter should expect to set it differently.

A concrete case where our order is wrong. Suppose your authored content is a junior analyst's first-week guess, and your deliberated content is a frontier model reasoning carefully over a well-specified prompt with the reasoning shown. Our order says the guess outranks the reasoning. For that system it plainly should not. The ordering is the parameter you tune; what the pattern requires is that you write down the order and justify it in public, not that you adopt ours.

Why we put deliberated one step above the floor

Because there is published, measured evidence of a specific failure mode in the domain this site models.

LLMs as Strategic Actors: Behavioral Alignment, Risk Calibration, and Argumentation Framing in Geopolitical Simulations

Solopova et al. · arXiv:2603.02128 · 2 March 2026

Evaluated six state-of-the-art models alongside human results across four real-world crisis simulation scenarios. Models approximated human decision patterns in early rounds but diverged over time. The finding that matters here: explanations across all models showed a strong normative-cooperative framing centred on stability, coordination and risk mitigation, with limited adversarial reasoning.

The scope limit, stated. That is evidence about argumentative framing in geopolitical crisis simulation. It is strong support for placing deliberated low in coalition and crisis modelling, where defection is the central dynamic and a model that under-models defection is wrong in the direction that matters most. It is weaker support for a general claim that language-model output is the least trustworthy non-empty class in every domain. We have not made that general claim and this page does not rest on one.

What that costs you, said plainly

Any value downstream of language-model reasoning caps at deliberated, no matter how much measured data it touches. A projection built from forty years of sourced observations and one model judgement is a deliberated value. It does not get to be modeled because most of its inputs were good.

That is the point of the rule, not a side effect of it. If judgement entered the chain, the output carries judgement's standing. Expect a large share of your most interesting output to end up wearing a low class. A system where the propagation rule never bites is a system whose labels are decorative.

Prior art — what this borrows

Very little here is new, and a page about provenance that obscured its own would be self-refuting. The genuinely novel part is narrow: a distinct class for language-model output, positioned by measured evidence of a specific failure mode, enforced in CI with no override. The machinery underneath is forty years old.

Lattice models of information flow

Denning · A Lattice Model of Secure Information Flow · 1976

Labels attached to values, propagating through computation, joining at the more restrictive label. Structurally this is the same mechanism. We changed what the labels mean and what happens at the top.

PROV

W3C Provenance Working Group · 2013

A full ontology for how an entity was derived, by which activity, attributed to which agent. Far more expressive than five ordered labels. Use it if you need to reconstruct a derivation; use something like this page if you need a reader to see standing at a glance.

Disclosure artefacts

Gebru et al., Datasheets for Datasets · Mitchell et al., Model Cards for Model Reporting

Established the obligation to ship provenance and limitations alongside an artefact. They document a system at the level of the whole; this documents it at the level of the individual value.

Database provenance

Why-provenance, how-provenance, semiring provenance

The closest true relative. It carries a full derivation expression per value. We carry a single ordered label instead, on purpose: a reader has to be able to see it in the layout, and a polynomial does not fit in a caption.

So how is this different from taint tracking?

Mechanically, barely. Both attach labels to values and join at the weaker one. The differences are purpose and terminal behaviour. Taint tracking asks a binary security question — did this value touch something untrusted — and the goal is to stop the value reaching a sink. This asks a graded epistemic question with five answers, and the goal is the opposite: the value should reach the reader, carrying its standing intact and rendered so that standing is visible. Taint failure means a leak. This failure means a reader mistakes an argument for a finding. That difference decides the design: taint labels can be invisible and usually are, whereas these labels are useless unless they are rendered, which is why each class here has a required visual register and why the register is part of the specification rather than a styling choice.

Enforced by a machine, not by discipline

A labelling convention maintained by good intentions degrades within weeks, because the failure mode is a tired person at 2am deciding one missing field is fine. So the classes are checked mechanically.

The companion specification — ARTIFACT_CONTRACT.md v1.1, in a separate repository — defines a run artifact format and a ten-check validator over it. The properties that matter for adoption:

  • Refuse by default. Anything the validator cannot affirmatively verify is a failure. There is no warning severity, and the data model has no severity field at all, so adding one requires a reviewed commit rather than a runtime decision.
  • No override flag. None. If a check is wrong it gets changed in a commit, not bypassed on a deadline. This is the load-bearing constraint and it is the one most likely to be quietly removed by a future maintainer.
  • Bare numbers fail. Every numeric value must be a typed object carrying its class, with a short, explicit, path-scoped allowlist for structural integers like counts and identifiers. A key-name allowlist is not sufficient — it admits any field called count anywhere in the tree, including places where a count is a real quantity carrying real provenance.
  • The propagation rule is check nine. Derived values must declare their inputs; the declared class is compared against the weakest resolved input. A derived value that cannot name what it came from is a failure, not a pass.
  • Identical in every context. The same binary runs locally before publication and in CI after it, so an artifact cannot pass one and fail the other. Where a check genuinely depends on environment — commit ancestry, for instance — the environment is passed in as an explicit argument rather than sensed, so the behaviour stays identical given identical inputs.

That specification is not published yet. When it is, this section becomes a link.

When this pattern will not help you

Three cases where the cost is real and the return is not.

  • Your system does not have a mix. If everything you emit is language-model output, every value gets the same class and the lattice does no work. The pattern earns its cost only where genuinely different kinds of claim sit next to each other and look alike.
  • Your output is prose, not values. Propagation is defined over composition — a derived number, computed from other numbers. Text does not compose that way. You can still label a block of prose, and you should, but you get the labelling and not the arithmetic, which is most of the value.
  • You do not control your own release gate. The no-override rule assumes you can afford to be blocked. That is a governance precondition, not a technical one, and in an organisation where shipping is someone else's decision the flag comes back within a quarter.

What it costs to adopt

  • Every numeric value becomes an object. Payload grows, and so does the friction of writing one by hand. This is the cost people underestimate.
  • You need the validator before you need it. Without mechanical enforcement the labels are accurate for about a week and then quietly stop being accurate, which is worse than not having them, because now the reader trusts something that is no longer true.
  • Your best output will wear a low class. There will be pressure — internal, reasonable-sounding, persistent — to reclassify. Every instance of that pressure is the rule working.
  • The class assignments are themselves authored. Deciding that a given value is modeled rather than authored is a judgement call, and it needs the same review as any other editorial decision. The system labels values; it does not label itself.

If you were implementing it

  • Enumerate your classes. You probably need fewer than five. The test is whether a reader would act differently on two values in different classes; if not, merge them.
  • Fix the order and publish the reasoning. This is the step that is actually hard, and the step most likely to be skipped. An unpublished ordering is an unaccountable one.
  • Make every value an object carrying its class and whatever that class requires — a source URL for measured, a rule id for computed, a stated reason for a gap.
  • Write the propagation function. It is about ten lines. The one on this page is the whole implementation, not a simplification of it.
  • Write the validator, and do not give it an override flag. Add a test that fails if someone adds one.
  • Give every class a visual register that differs in kind — solid, double, dashed, dotted — never in shade. A reader must not have to compare two greys to tell a measurement from a judgement call, and shade differences do not survive a screenshot, a projector, or a colour-blind reader.
Status, so this page does not overstate itself. This system is specified and machine-enforceable. It is not battle-tested. Three of the five classes carry real content on this site today; deliberated is reserved and nothing generates it yet, and unknown exists in the specification ahead of the engine that will produce it. The validator is written as a specification with fixtures, not yet as a component with a year of runs behind it. Treat this as a design that has been thought through and mechanically checked, not as one that has survived contact with scale.
