# Coordination-Experiment Fit Analysis: aicivsim

Read-only analysis. No code was built or changed. Verdict: **aicivsim is not a fit** for a multi-agent coordination task — it fails all three criteria, because it fails the prior question of whether a simulation exists at all. There is no running simulation, no agents, and no decision space anywhere in this repository. It is a static Next.js site presenting pre-authored scenario data across six dashboards (see `CLAUDE.md`).

---

## 1. Non-local coupling — **No**

**Verdict: No — there is nothing to couple.** The repo contains no code that models more than one agent/entity, so the question "would splitting agents across workers change the result" doesn't apply; there's only ever one entity being tracked.

Evidence:
- `public/data/simulation.json` — the only time-evolving state in the repo — has top-level shape `{ scenario, runs: [...] }` with exactly 12 `runs`. Each run is one fixed parameter tuple (`civic_dividend_rate`, `ai_charter`, `climate_capex_share`) mapped to **one** 50-year `trajectory` of a **single** aggregate state (population/economy/climate/governance fields). The 12 runs are 12 alternate timelines of the *same* one civilization under different policies — not 12 civilizations coexisting and interacting. Confirmed by direct inspection (`node -e "require('./public/data/simulation.json')"`): `runs.length === 12`, each `trajectory.length === 50`, each trajectory entry has one scalar value per field, no per-agent or per-region breakdown.
- No file in the repo defines a per-agent update function, a neighbor/adjacency structure, an interaction term, or any function of the form "agent A's state affects agent B's state." A repo-wide search for simulation logic terms (`generat*`, `engine*`, `scenario*` as filenames) returned nothing — there is no generator script at all, committed or otherwise.
- The closest thing to "combining effects" is `app/strategy/page.tsx`'s Impact Simulator, which sums selected static actions' `co2_kg_yr` values (`POLICY_ACTIONS.reduce((a,c) => a + c.co2_kg_yr, 0)`, `app/strategy/page.tsx:824`). This is a linear sum over independent static line items — the textbook case of a *trivially partitionable* computation (order- and grouping-independent), the opposite of non-local coupling.

There is no interdependency to preserve or lose by parallelizing, because there is no multi-entity model to begin with.

## 2. Verifiable target states — **No (data is static, not generated by rules)**

**Verdict: No**, with an important nuance. The *shape* of the state is well-defined and could in principle support target-state checks (each year has typed numeric fields: `gdp`, `gini`, `annual_emissions`, `resilience_score`, etc. — see `simulation.json` trajectory entries and the `SnapshotState`/`RunData` TypeScript interfaces in `app/simulation/page.tsx:21-31`). So "check whether metric X crossed threshold Y by year Z" is mechanically answerable against the existing JSON.

But that's checking pre-written fiction, not verifying a simulation's behavior:
- There is no update rule in the codebase that produces these numbers from a prior state — no `step()`/`tick()`/transition function exists anywhere. The 50-year, 12-branch trajectory is a finished artifact with no generator committed to the repo (confirmed: no scripts directory, no `package.json` script beyond `dev`/`build`/`start`/`lint`, no reference to producing `simulation.json`).
- Values are static and fixed per branch; you cannot pose a *new* target state and have the sim run toward or away from it, because nothing runs. You can only look up whether one of the 12 pre-existing canned trajectories happens to satisfy your check.
- The other dashboards (`climate.json`'s four scenario arrays, `strategy.tsx`'s `strategyScores`/`aggregateProjection` objects) are the same pattern: hand-typed arrays keyed by scenario name, not rule output (`app/strategy/page.tsx:256-271` shows literal authored scores like `score: 78, trend: "improving"` with hand-written notes — not derived from any formula).

If the coordination experiment needs a scoreable target-state check, this repo would supply the *checking* half (the JSON schema is fine for that) but none of the *generating* half — you'd be building a simulation engine from scratch, not adapting one.

## 3. Semantic vs. numeric levers — **No — and moot, since there's no agent to hold a lever**

**Verdict: No.** Every "lever" in the app is either a fixed categorical/numeric branch-selector or a static pre-scored menu item; none require reasoning, negotiation, or intent, and none are exercised by an autonomous entity — only by the human site visitor via UI clicks.

Evidence:
- `simulation.json`'s branch parameters are two booleans/discrete-numeric knobs (`civic_dividend_rate` ∈ {0.02, 0.05, 0.1}, `ai_charter` ∈ {false, true}, `climate_capex_share` ∈ {0.15, 0.25}) — a fixed 3×2×2 grid a human picks from a dropdown in `app/simulation/page.tsx`; nothing decides or negotiates a value.
- `strategy/page.tsx`'s `POLICY_ACTIONS`/`SIM_ACTIONS` are static cards with pre-assigned `cost`, `difficulty`, `impact_score`, `co2_kg_yr` fields (`app/strategy/page.tsx:783-813`) — a classical optimizer (or a spreadsheet) could already rank/select among these; nothing about them requires natural-language reasoning.
- No LLM call, prompt, or agent-decision code exists anywhere in `app/` or `lib/` (repo-wide grep for `openai`/`OPENAI` found zero hits outside `package.json`'s dependency list, and no `app/api` directory exists to host such a call). The `openai` package is declared but dead weight in this checkout.
- Governance/civic-assembly content (`governance.json`) describes citizen deliberation, sortition, and charter pillars in **prose** (`charter.pillars[].principles`, etc.) — this is a narrative description of a governance *design*, not an implemented decision space any entity (human or LLM) actually exercises in code.

---

## Summary

aicivsim fails all three criteria, but the deeper finding is that the premise doesn't hold: **there is no simulation engine in this repository to evaluate.** It's a static-export marketing/vision site (Next.js + Recharts) that renders one hand-authored global trajectory across 12 pre-baked policy branches, four hand-authored climate scenario arrays, and several pages of hardcoded scoring tables and UX-journey prose. There are no multiple agents (so non-local coupling is inapplicable rather than merely weak), no generative rules producing checkable state (so target-state verification would check fiction, not behavior), and no decision space of any kind, semantic or numeric, being exercised by anything other than a human clicking through a dashboard.

If the goal is a substrate for irreducible, verifiable, semantically-driven multi-agent coordination, this repo offers essentially nothing to build on beyond UI/chart scaffolding and thematic flavor (civic dividends, AI charters, climate branches) that could inspire a *new* simulation's premise. The actual engine — agents, coupling, update rules, a decision space — would need to be designed and built from scratch; none of it exists today, in whole or in part.
